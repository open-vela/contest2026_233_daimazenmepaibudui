## 修的是什么

NuttX 音频上层（`nuttx/audio/audio.c`）的**会话记账在说谎**，详见
`patches/README.md` 的「`nuttx-audio-drain-fix.patch` — `audio/audio.c` 的三次
状态机钉死」。一句话：一个假的 `priv->state = RUNNING` 就能让**所有**
`audio_stop()` 进不了真停硬件那个分支 → 硬件停不下来 → 永远没人发 COMPLETE
→ 状态机钉死 → 之后 CONFIGURE/START 全被静默吞掉却照样返回 OK。

补丁：`patches/nuttx-audio-drain-fix.patch`
（已按 README 第 23-24 行的硬判据验过：`git apply --check --reverse` **通过**，
= 与工作区逐字对应。）

## ⚠️ 未定论的地方（照实记，别当已验证）

修复里有两笔：

1. **被吞的 START/RESUME/PAUSE/CONFIGURE 不再写 `priv->state`**
   —— 记账只在真转发给驱动时才写。
2. **抢占后 `audio_forget_sessions()` 强制作废别人的陈旧记账**。

我原先预告过：`audio: 清掉 N 个陈旧的会话记账` **每次回复起播都该打一次**。
**实测它一次都没打（0 次）。**

回看日志才明白：hello_app 自己是**先把麦停干净、再起播**的
（`AUDIO_IN: stopped` 早于 `AUDIO: hw_start 真跑了：playback=1`），
**根本没走抢占那条路**。所以「抢占留下陈旧记账」这个触发点在这 150 秒里压根
没发生过。

那么真正下毒的多半是第 1 笔。**但也可能只是重启后账本本来就干净、压力还没到。**
现在**不能下定论**，所以第 2 笔不能算「已验证的修复」。

### 要再压的场景（下次上板照这个来）

1. **AI 正在说话时大声插话**（半双工抢占真正会被触发 —— 这是唯一能验到第 2 笔的场景）
2. 说完立刻接着说下一句，不等它答
3. 连说 **10 轮以上**，中间别停

串口出现下面任意一行就记下来（**出现本身不是 bug，是修复在动手**；
连着刷屏才是没修透）：

```
audio: 清掉 N 个陈旧的会话记账（半双工抢占拆掉了别人的会话）
audio: START 被吞 / CONFIGURE 被吞 / PAUSE 被吞 / RESUME 被吞
audio: STOP 没停到硬件（status=… nstate=…，本 fd 记账 …）
```

### 判定「好了」的硬指标

每次开麦，串口必须有：

```
AUDIO: hw_start 真跑了：playback=0
```

只有 `AUDIO_IN: started` 而**没有**这一行 = 状态机还被吞，病没好。
