## 1. 报警语音取消「没事」听不到

### 真机现象

- 报警确认页弹出后说「没事」没有反应，只能等 10 秒超时或用手点按钮；
- 串口：`[volc_asr] No text recognized`，下一轮又 `[轮次] ★ 卡在 ASR 相位 … 作废`。

### 根因与修复

| 根因 | 修复 |
|---|---|
| ASR 上传前只补静音、不抬电平；听窗里的「没事」原始峰值仅 444（正常说话 3000+），火山判“无人声” | `ai_companion_main.c`：追问/急救短句不足 1 秒补静音到 1 秒；**所有对话**音频峰值低于 3000 时线性增益到约 6000（上限 6×），只改送 ASR 的副本 |
| 报警期间 AI 仍播「我刚才没听清楚，您再说一遍好吗？」（2.7 秒/次），半双工抢走急救听窗的麦克风 | 置位处 + 播放处双重判断：`voice_emerg_is_active()` 时一律丢弃「没听清 / 识别失败」提示 |
| 「短句即没事」用 `strlen()` 按**字节**算：`我没事，取消报警` = 24 字节 > 15，被判成噪音 | `voice_emerg.c`：改成按 UTF-8 字符数（8 个字 ≤ 15） |
| 火山对报警听窗的「没事」仍会返回 `No text recognized(-61)` | `ai_companion_main.c` + `mimo_voice.c`：火山空结果时用 **MiMo ASR 二次识别同一段（已增益/补静音的）音频**；只采纳包含「没事 / 不用 / 没有」的结果，命中即 `voice_emerg_cancel()`，避免 MiMo 幻觉出别的字 |

### 验证日志

```
[AI] 追问短句增益 x5（原始峰值 1064）
[AI] 追问短句补静音：8000 → 16000 帧
[volc_asr] Recognized: 这
[急救] 报警中收到短句（≤15 字，判为「没事」）：这
[急救] 老人说没事 -> 停铃，**不通知家人**
```

## 2. 界面「重置」后语音永久失效

### 真机现象

点语音聊天页的「重置」→ hello_app 重新拉起 → 之后每段语音都投进没人处理的信号量，
30 秒后 `[轮次] ★ 轮 N 卡在 ASR 相位 30006 ms，作废`，整机“说了没反应”。

### 根因

上一代识别线程正卡在 ASR 网络调用里（不在 `sem_wait`），主线程收尾等不到它；
static 的 `g_dlg_thread_valid / g_dlg_worker_alive` 仍是 true，新实例判断
「识别线程已在跑（接管路径，沿用）」→ 不再建线程 → 信号量永远没人取。

### 修复

`ai_companion_main.c` 增加**实例代际**：

- 每次真正初始化 `g_app_instance++`；
- 工作线程记录自己那一代，循环里发现代变了立即退出；
- 新实例建线程条件带上「工作线程代 == 当前代」，对不上就新建一条；
- 旧线程退出时只清自己那一代的 `alive`，不碰当前代。

验证日志：

```
[启动] 实例代际 = 2
[识别] 识别线程进入服务（代 2）
[启动] 实例代际 = 3
[识别] 识别线程进入服务（代 3）
[识别] 上一代识别线程退出（代 2），不碰当前代
```

## 3. 天气/实时检索拖垮轮次

### 真机现象

天气请求两次 TLS 共耗时约 27 秒，轮次看门狗仍按 **ASR 相位 30 秒**计时，
把这一轮作废；随后数轮接连 `卡在 ASR 相位`。天气其实查成了、TTS 也念了，
但轮次状态已经乱掉。

### 修复

`weather_fast_try()` / `realtime_try()` 在发起网络请求**之前**
`round_phase_set(ROUND_PHASE_LLM)`（上限 45 秒），不再被误判为 ASR 卡死。

验证：连问两次天气，两轮均正常回答，串口 0 次 `卡在 ASR 相位`。

## 4. TLS 出站连接只涨不降（内核 TCP 连接池泄漏）

### 真机指纹

```
[TCP] pool=28/128 act=27 st[D21 …] peers[1883:2 443:25]
```

3 分钟测试 `nalloc` 6 → 29，其中 21 条停在 `TCP_CLOSED`、`crefs=0`、对端端口 0；
到 128 条后 `socket()` 返回 `ENOMEM`，语音/天气/推送一起失败。

### 根因（代码级）

1. `tcp_close_work()` 先置 `TCP_CLOSE_DIRECT`，再判断
   `crefs==0 && state==TCP_CLOSED`；它执行时状态还是 `FIN_WAIT_2`，
   于是跳过 `tcp_free`，**之后没有任何人再回调它**；
2. 2MSL 后 `tcp_timer` 把状态置 `TCP_CLOSED` 并调 `tcp_callback(TCP_TIMEDOUT)`，
   但 close 回调已在第 1 步的 `end_wait` 里释放，没人接；
3. 条目从此挂在 active 链表上，只占 mempool 不释放。

### 修复（NuttX 内核，两处）

- `net/tcp/tcp_timer.c`：TIME_WAIT 到期、`crefs==0` 且 `TCP_CLOSE_DIRECT` 时
  直接 `tcp_free`（与 SYN_RCVD 超时分支同样先解锁再 free）；
- `net/tcp/tcp_conn.c`：池满回收条件放宽——已跑过 close work 的 CLOSED 条目
  也允许复用；原来因 `TCP_CLOSE_ARRANGED` 被永久排除。
- `net/tcp/tcp_conn.c`（`tcp_alloc`）：**主动回收**——每新建一条 TCP 连接，
  顺手回收一条「`crefs==0` + `TCP_CLOSED` + `TCP_CLOSE_DIRECT`」的僵尸条目。
  真机发现服务端 RST/短连接会绕过 TIME_WAIT 直达 CLOSED，单靠定时器修补不够；
  这条兜底保证池子不会只涨不降。

### 验证日志（2026-11-02 23:48~23:53，真机运行 45 分钟）

```
[TCP] pool=6/128 act=5 st[D0 …] peers[1883:2 443:3]
[TCP] pool=5/128 act=4 st[D0 …] peers[1883:2 443:2]
[TCP] pool=7/128 act=6 st[D1 …] peers[1883:2 443:4]
[TCP] pool=5/128 act=4 st[D0 …] peers[1883:2 443:2]
```

修复前同长度测试 `pool 6→29 / D0→21` 单调上涨；现在稳定在 `pool 5~7 / D0~D1`。

## 5. 实时信息功能简化

- 删除「娱乐/体育/财经…」分类猜测和「第X条详细说说」专门路径；
- 改为：带 `新闻/最新/实时/热点/头条/消息…` 的问题，把**用户原话**
  （去掉 ASR 开头的「你好你好，」）直接交 Tavily 通用 `web_search`，
  没结果再退 `news_search`；
- 输出缓冲 1024 → **12288 字节**（旧版 1024 字节把 10 条截成 1 条，
  串口 `Tavily OK: 1023 bytes` 就是证据）；
- 正文过滤版权/页脚/导航行，标题去掉 ` | 来源` 后缀。
